# DESIGN DECISIONS (v2)

v1 (cash book) decisions are in `docs/v1/DECISIONS.md`; those still in force are restated here where needed.
Rule when in doubt: choose the option that is safer from an accounting standpoint.

| # | Issue | Decision | Rationale |
|---|---|---|---|
| D-v2-01 | UI framework | Keep **Jinja2 + HTMX 2 + Alpine 3 + Tailwind v4**, redo the design system | The user allowed Jinja; whether it looks good depends on design, not on the framework. No Node at runtime, a single Python process, fast server rendering, print templates and web pages share one engine. An SPA (React/Svelte) would mean rewriting the whole API + build pipeline with no added value for data-entry work. |
| D-v2-02 | Entry model | **Line = debit/credit pair** (debit account, credit account, amount) with partner/bank account per side | How Vietnamese accountants record entries; the contra account on S03b/S04b/S05 is always determined; every line balances on its own. |
| D-v2-03 | Data source | All ledgers and reports read `journal.queries.ledger_source` (posted vouchers ∪ opening balances) | A single source; no parallel figures drifting apart. |
| D-v2-04 | Opening balances | Separate `opening_balances` table; in the ledger it carries a "before all periods" date (1900-01-01), so every reporting period starting on or before the accounting start date gets the correct opening balance; editable while no period is locked | Not a "voucher"; keeps the immutability triggers simple; identical results on SQLite and PostgreSQL (found when running the tests on PostgreSQL). |
| D-v2-05 | Multi-company | One DB, a `company_id` column + automatic filtering attached to the session (layer 2) | Simple to operate; isolation verified by tests. |
| D-v2-06 | Superadmin | Does not automatically see customers' books | Trust of SaaS customers. |
| D-v2-07 | Posting serialization | Row lock on `companies` (PostgreSQL) + process lock for SQLite | Removes the single-worker limit when using PostgreSQL. |
| D-v2-08 | Voucher numbers | Assigned at posting (keeps v1 D1), sequential per type + year; default format `{prefix}{year}-{seq:04d}`; prefix configurable | Deleting drafts does not create gaps. Resets every year when the format contains `{year}`. |
| D-v2-09 | Future dates | The engine allows them (month-end depreciation, closing entries); the cash/bank modules block them themselves | Real cash receipts/payments cannot be in the future; accruals can. |
| D-v2-10 | No negative balances | Accounts flagged `no_negative` (1111, 1112, 1121, 1122 per bank account), retroactive check after flush, rollback on violation; modules can register more (negative stock) | Keeps the v1 rule, extended to bank accounts. |
| D-v2-11 | API token permissions | Only `.view/.export` (read) and `.create` (write_draft); no posting, no administration | External APIs/agents cannot post by themselves. |
| D-v2-12 | HTKK XML | Generate the HTKK layout from the **validation schemas shipped inside HTKK** (`InterfaceTemplates/*.xsd`, HTKK 5.4.5 and 5.6.4): 01/GTGT = form 842 v2.8.3, financial statements TT133 = 683 v2.3.2 (B01a + B02 + B03 direct + F01), 03/TNDN = 892 v2.9.4 (+ 03-1A), 05/QTT-TNCN = 953 v2.9.3 (+ 05-1, 05-2; new ward-level envelope). Files are unsigned (no `CKyDTu`); the shared envelope is `app/core/htkk.py`. Tests validate against the XSDs when `HTKK_XSD_DIR` points to them; the XSDs are not redistributed. Still say "open in HTKK before filing" | The schemas are the only machine-readable specification; no vendor download page exists. Open points: the period encoding of the BCTC file (`kieuKy` – HTKK pre-fills `D`), whether the portal accepts a service id other than HTKK, and the coming Circular 89/2026 versions. |
| D-v2-13 | 8% VAT rate | Declared together with the 10% group ([32]/[33]) at actual values + tax-reduction appendix under Decree 174/2025 | Current guidance while the tax reduction applies. |
| D-v2-14 | Payroll/tax parameters | Effective-dated, editable table: family deductions VND 15.5M/6.2M and the 5-bracket schedule from 01/01/2026; before that 11M/4.4M and 7 brackets | The law changes often; do not hard-code. |
| D-v2-15 | Depreciation | Straight-line, monthly, starting in the month the asset is recorded (option: the following month) | Common in small businesses, easy to reconcile. |
| D-v2-16 | Inventory issue costing | Periodic (monthly) weighted average per item + warehouse; COGS vouchers are generated by "Tính giá xuất kho" (Stock costing) | Most common in small businesses; keeps posted vouchers immutable. |
| D-v2-17 | Receivables/payables | Debt aging computed FIFO (payments applied to the oldest invoice) | Small businesses need no manual matching; manual matching can be added later. |
| D-v2-18 | AI writing data | AI tools only create **drafts**; an authorized person posts them | Responsibility for the figures lies with the signer (Article 28, Circular 99). |
| D-v2-19 | AI protocol | OpenAI Chat Completions (tools, SSE streaming) via httpx | The common standard of most providers and self-hosted servers. |
| D-v2-20 | Product name | Working name "NVIAI Kế toán" (now VFAS, see D-v2-27), display name changed via `PRODUCT_NAME`; do not use "eTax" | Avoids confusion with the Tax Department's e-tax portal. |
| D-v2-21 | Migrations | During development: `create_all` + triggers; for releases: a single Alembic v2 baseline migration | v1 was never deployed for real, so no v1 → v2 data migration is needed (v1 cash book data is re-entered through Excel import). |
| D-v2-22 | Importing historical cash books | `journal.service.post_batch` posts in bulk through the engine, retroactive negative check on account 1111 only | Old data has 1121 contra lines while bank balances are not yet entered; module checks and validators still run. |
| D-v2-23 | Translations | One shared catalog, the module wins on duplicate keys; `tools/i18n_scan.py` + a test catch missing strings | Module translations fit their context better than the v1 ones. Error messages containing dynamic figures are shown in Vietnamese. |
| D-v2-24 | CSP | `script-src 'self' 'unsafe-eval'` (Alpine needs eval), no inline scripts left; only `/api/docs` has its own CSP allowing the Swagger CDN | Smaller XSS surface. |
| D-v2-25 | AI calling internal URLs | SaaS mode (`ALLOW_SIGNUP=true`) blocks internal/loopback addresses and requires https; opened with `AI_ALLOW_PRIVATE_URLS=1`; allowed for self-hosted installs (Ollama) | SSRF protection. |
| D-v2-26 | API rate limit | 60 requests/minute/token, counted in the DB (correct with multiple workers) | Originally counted in memory; the 14/10/2026 security review moved it to the DB. |
| D-v2-27 | Name, license | **VFAS – VietNam Free Accounting Software**, open source under the **MIT License**, copyright NVIAI CO., LTD.; cookie/token prefix `vfas_`; keep `NVKENC1` (encrypted backup header) and the `nvk-secrets` key-derivation string so old data stays readable | Free for businesses and the widest possible reuse (integrators may embed it, including in closed products). AGPL-3.0 was considered first; the maintainer chose MIT on 2026-10-14. |
| D-v2-28 | Security | Per the 14/10/2026 review (`docs/SECURITY-GUIDE.md`): client IPs trusted only from proxies in `FORWARDED_ALLOW_IPS`; failed-login limits stored in the DB; `/setup` requires a setup code; Bearer tokens only for `/api/`; payroll hidden from users without `payroll.view`; the platform's AI key is only sent to `AI_DEFAULT_BASE_URL` | Closes the High/Medium findings, each with a regression test. |
| D-v2-29 | Email (SMTP) | Plain `smtplib` with STARTTLS/SSL, no extra dependency; one template per email with `subject`/`text`/`html` blocks (translated like the UI); verification and reset links are **stateless signed tokens** (itsdangerous, `SECRET_KEY`) – the reset token embeds a fingerprint of the password hash, so it works once and dies with any password change; reset/verification emails are sent in a background thread (no timing oracle, no blocked worker), invitations synchronously so the inviter sees failures; verification is required only for self sign-up (`EMAIL_VERIFICATION=auto`) | No new tables or workers to operate; accounts created by an administrator or through an invitation are vouched for; rotating `SECRET_KEY` invalidates outstanding links, which is acceptable. |
| D-v2-30 | Issuing e-invoices | Separate `einvoice` module with one adapter per provider behind `EInvoiceProvider`; only **draft** sales vouchers are issued (the number must reach the voucher and its VAT lines before they become immutable), dated today; outbox row + idempotency key committed before every call, lookup-before-resend on timeouts; issued vouchers locked through posting validators/hooks; HSM signing only; adjustment invoices only where the provider documents a decrease; no replacement/04-SS | Never two invoices for one sale and never an invoice without its booking; adapters are written from official docs/WSDLs and working clients (field names), not copied from LGPL code; untested provider behaviour is listed in docs/EINVOICE.md instead of guessed silently. |
| D-v2-31 | Accounting regimes | `companies.regime` = `tt133` \| `tt99` \| `tt58`, defined in `app/core/regimes.py` (chart, default accounts by role, printed form codes, "Ban hành theo / Kèm theo" line, statement set). **TT99/2025** (27/10/2025, from FY2026, applies to *all* enterprises; SMEs may choose it): chart of Appendix II with software-opened details 1111/1112/1121/1122/5111–5118 (Art. 11), 3524 used for "other provisions" (the list says 3525, the account text 3524); B01-DN with short/long-term lines (rule per account + company lists `b01.long_term`/`short_term`, judgement warnings), B02-DN, B03-DN direct; ledgers renamed to the Appendix III codes (S03a/S03b-DN, S06-DN trial balance, S07/S07a/S08-DN cash and bank, S10/S11/S12-DN inventory, S21/S23-DN assets – the last two groups follow the TT200 numbering kept by TT99). **TT58/2026** (25/5/2026, micro enterprises, from FY starting ≥ 01/7/2026): no chart of accounts in the circular, so the books stay double-entry on the TT133 chart and only B01-DNSN/B02-DNSN carry TT58 form codes; TT133 books print as internal books. The regime can change only while the company has no voucher and no opening balance | Earlier docs wrongly called TT99 a large-enterprise regime and TT58 a chart: both were checked in the signed circulars (research of 14/10/2026). Modules ask for accounts by role (`expense_staff`, `unemployment_insurance`…) because TT99 reuses codes with other meanings (6421/6422, 3386, 2281). The HTKK BCTC XML (form 683) exists only for TT133. |

## Module decisions (details and sources: `docs/requests/*.md`)

**General ledger, financial statements (`gl`)** – TT133 line codes cross-checked against ketoanthienung, hoatieu, thuvienphapluat (`docs/requests/gl.md`).
- B01a-DNN: total assets code 200 = total liabilities and equity code 500. Code 110 includes only 111 + 112 (term deposits go to 122).
  Unclosed balances of class 5–9 accounts are added to 417 with a warning. Dual-nature accounts are split by partner.
- B02-DNN uses movements excluding closing (KC) vouchers; line 23 (interest expense) requires a 635 sub-account whose name contains "lãi vay" (interest).
- B03-DNN uses the direct method by the contra account of the cash line, overridable via `cash_flow`; payments to 331 default to code 02.
- Re-running the closing = cancelling the previous closing (KC) vouchers; 4212 → 4211 on 01/01 of the following year. B09 is a template pre-filled with figures.

**Sales, purchases, tax (`sales`, `purchases`, `vat`, `debts`)** – `docs/requests/vat.md`.
- VAT filing period by posting date; 8% declared together with the 10% group + tax-reduction appendix under Decree 174/2025.
- [23]/[24] also include non-deductible invoices, [25] only the deductible part; [22] takes [43] from the saved previous-period return;
  a previous period cannot be reopened once the next period is finalized.
- The HTKK 01/GTGT XML follows the commonly seen structure, **no official XSD yet** – constants isolated in `vat/htkk.py`; the file must be
  opened in HTKK and checked before filing. The CIT worksheet is for reference (internal codes); rates per Law 67/2025.
- XML invoices: discounts are deducted from lines with the same VAT rate; duplicate detection by tax code + template + series + number; digital signatures are not verified.
- Filing calendar: monthly VAT/PIT on the 20th, quarterly on the last day of the first month of the next quarter, provisional CIT on the 30th, annual finalization + financial statements at the end of March;
  Saturday/Sunday deadlines move to Monday (public holidays not yet handled).

**Inventory (`inventory`)** – `docs/requests/inventory.md`.
- Goods issue notes (XK) and stock transfers (DC) are separate inventory documents; their values are posted through COGS (GV) vouchers when monthly costing runs.
- "Cho phép xuất âm kho" (Allow negative stock) setting (off by default) for companies that do not track inventory.
- Inventory book codes S06/S07/S08-DNN and notes 01-VT/02-VT follow advisory sources – need checking against the original text.

**Fixed assets, payroll (`assets`, `payroll`)** – `docs/requests/payroll.md`.
- Payroll/tax parameters are effective-dated and editable: family deductions VND 15.5M/6.2M and the 5-bracket schedule from 01/01/2026; base salary 2,530,000
  from 01/7/2026 (Decree 161/2026); 10% withholding threshold for contracts under 3 months VND 5M from 01/7/2026 (Decree 253/2026 – one primary source).
- Parameters apply as of the last day of the payroll month; insurance is computed on the full month's insurable salary, not prorated by working days.
- Form codes S09-DNN, S11-DNN, 06-TSCĐ, 02-LĐTL follow advisory sources – need checking against the original text.

**Cash (`cash`, `bank`)** – `docs/requests/cash_bank.md`. Importing old cash books: parent accounts are mapped to detail accounts (3338 → 33382,
341 → 3411), accounts that require a partner get a placeholder partner, and a placeholder bank account is created when none exists.
